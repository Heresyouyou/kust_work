# 知识点拆分逻辑 v2（2026-10-23）

> 适用范围：`scripts/kp_extract.py`（DeepSeek API 管线）与 `scripts/agent_ingest.py`（Agent 亲自入库）
> 共用引擎：`scripts/kp_select.py`　｜　团队画像：`config/team_focus.yaml`
> 取代：旧版「一次调用、提示词写死最多 6 条」的做法

---

## 1. 为什么要重写（诊断）

对全库 1543 篇 / 9315 条知识点做统计，三个硬事实：

| 现象 | 数据 | 含义 |
|---|---|---|
| 条数撞上限 | **1469 / 1543 篇恰好 6 条（95.2%）** | 模型把「最多 6 个」当成了目标，条数由**名额**决定，不是信息密度 |
| 定量内容比例低 | 45.4% 的条目含带单位数值 | 过半条目在讲定性描述 |
| 无「漏点」检测 | 旧流程没有任何覆盖校验 | 摘要/结论里的关键结论可能一条知识点都没对应上 |

根因不在模型能力，而在**判据缺位**：提示词只给了「宁缺毋滥」这种主观要求，
没有可执行的判定标准，模型只能按名额补齐。

## 2. 收录判据（用户口径，2026-10-23）

一条知识点值不值得收，只问一件事：

> **它能给团队未来的研究带来多少价值？今后做同类研究时，还能不能再用到它？**

典型可复用形态：

- 相近研究区的地球动力环境、大地构造背景 → **换区可类比**
- 同一矿种、同一矿床类型的研究 → **直接对标**
- 创新性的方法、技术、流程、参数设置 → **可迁移**
- 对地质现象的解释方法与判别判据 → **可借鉴**

因此「数值多不多」不是价值核心。一条只描述某样品斜长石含量的记录，数字再多也换不了场景；
一句「高 Sr/Y + 负 εHf 指示加厚下地壳」，零数值却能在几十个矿区复用。

**价值判断本质主观，所以最终决定里给模型留 40% 的空间**（见 §3.4）。

## 3. 算法：候选 → 硬闸门 → 规则分 → 60/40 融合 → 去重 → 覆盖校验

### 3.1 候选抽取（LLM，1 次调用）
模型不再「直接写 6 条」，而是**穷尽式列候选**（5–14 条），每条带：

```json
{"title": "≤26字", "body": "100–260字", "type": "定量结果", "reuse": "标定参照",
 "why": "今后怎么用", "value": 9, "verdict": "keep",
 "numbers": ["95.4±1.2 Ma"], "quote": "逐字原文片段", "evidence": "L120-L126",
 "tags": ["…"]}
```

强制要求（提示词 + 代码双保险）：

- **覆盖契约**：摘要/结论里每一个带数值的结论，至少对应一条候选；
- **逐字引文**：`quote` 必须能在原文里按子串查到（允许空白/折行/标点差异）；
- **原子化**：一条只讲一件事；
- **本文语言**：中文论文用中文写，**英文论文必须用英文写**（禁回译，与条目规则一致）。

### 3.2 硬闸门（只判「真假」，不判「价值」）
| 闸门 | 处理 |
|---|---|
| 数值在原文找不到 | 直接出局 `unverified_number`（这是「编数」的硬证据） |
| 噪声（图表题注/征稿简则/致谢） | 出局 `noise` |
| 引文对不上 | **不判死**，扣 0.08 分并记 `quote_weak`（PDF 抽字常坏，硬判会误杀好条目） |
| 证据定位非行号（Agent 模式的「内容提要（7.2…）」） | 只告警，不拦（既有约定，只是不可机读） |

### 3.3 规则分（60% 权重，可复现、可审计）
权重按「换场景还能不能用」排列：

| 维度 | 权重 | 口径 |
|---|---|---|
| 复用模式 | 0.34 | 解释借鉴 1.00 / 方法迁移 0.96 / 类比参照 0.90 / 标定参照 0.82 / 本区事实 0.40 |
| 可迁移信号 | 0.22 | 明说「可作判据/适用/通常/判别图/端元/阈值」→ 1.0；只有因果机制 → 0.6；只有定位 → 0.25 |
| 团队相关 | 0.18 | 命中 `config/team_focus.yaml`（矿种/矿床类型/矿物/构造背景/方法/解释范式），3 项饱和 |
| 参照值 | 0.12 | 带单位数值密度，3 个饱和（供横向对比，不是越多越好） |
| 命名实体 | 0.10 | 地名/矿床/岩体/矿物/同位素符号 —— 决定可检索性 |
| 篇幅形状 | 0.04 | 中文 100–380 字最佳 |

扣分项：句首元叙述 −0.30、句尾套话 −0.08、噪声 −0.40、正文 <40 字 −0.25、
「本区事实且无团队相关且无可迁移信号」−0.12。

### 3.4 60/40 融合（用户口径：主观判断要有空间）
```
融合分 = 0.60 × 规则分 + 0.40 × (模型 value / 10)
```
- `value` 是模型对「对团队今后的复用价值」的 0–10 打分，提示词要求拉开差距；
- 模型可用 `verdict: "must"` 强行保留（**每篇最多 2 条**，绕过阈值但不绕过硬闸门）；
- 模型可用 `verdict: "drop"` 显式否决（规则分再高也尊重，记 `ai_veto`）；
- 全部决策记入 `logs/kp_select.jsonl`（含被丢弃条目的分数与原因），可回溯。

### 3.5 去重（三级）
| 判据 | 阈值 | 抓什么 |
|---|---|---|
| 正文相似度（3-gram + 数值重叠） | ≥0.62 | 同一事实的两种写法 |
| 标题主题相似 | ≥0.62 | 换了个说法的同主题 |
| **同源数据**（数值集合重叠 ≥50% 且标题相近） | — | 同一批测试数据被拆成 4 条（实测锆石 Hf 数据碎成「Lu-Hf 特征」「Hf 特征」「U-Pb 定年」「U-Pb 年龄」） |

`本区事实` 每篇最多留 1 条（按定义不可迁移，否则样品描述能刷满名额）。

### 3.6 覆盖校验与补抽
- 从摘要与结论里抽「带单位数值的结论句」作为槽位（≤10 个）；
- 选完按**最终留下的条目**重算覆盖率（不能按候选算，否则虚报）；
- 覆盖率 < 0.6 且有缺口 → 追加**一次**补抽调用（同一段文本，前缀缓存命中，约 1/10 价），
  补抽候选与原候选合并后按同一套规则重选，单轮最多补 3 条。

### 3.7 条数
`k` **由通过阈值的候选数决定**，没有下限：0 条是合法结果（征稿简则、书评、
纯工程地质描述、与本团队方向无关的论文）。上限 8 条。

## 4. 校准与实测

对全库 9315 条历史知识点用规则分回算（`kp_select.py audit-existing`）：

| 指标 | 值 |
|---|---|
| 分数分位 p10/p50/p90 | 0.494 / 0.719 / 0.894 |
| 低于 0.40（规则分下限） | 4.6% |
| 按新规则（绝对 + 相对 + 去重）重选后的条数分布 | 0:1 / 1:4 / 2:11 / 3:46 / 4:128 / 5:406 / 6:907 / 7:24 / 8:16 |

即：历史库重选后平均 **5.5 条**（原固定 6 条），少的正是分数尾巴上的填充项；
分布也从「95% 全 6」变成 0–8 的连续谱。

## 5. 工具与运维

```bash
PY=venv/Scripts/python.exe

# 全库打分审计（不调 API）：分数分位、低分样例、同篇重复、重选后条数分布
$PY scripts/kp_select.py audit-existing --show 20

# 看单篇的覆盖槽位与命中情况
$PY scripts/kp_select.py coverage 13266c4c7b99

# 单篇调试（不落盘）
GEOKB_KP_DEBUG=1 $PY scripts/kp_extract.py --sha <sha> --dry-run --force

# 写入到临时目录（不动生产内容，验证产物格式）
GEOKB_KP_OUT=/tmp/kptest $PY scripts/kp_extract.py --sha <sha> --force
```

**算法升级后重跑旧条目**（默认不重跑，避免误触发全库）：

```bash
$PY scripts/kp_extract.py --redo-version 2.0 8 200
```

`state/kp_done.jsonl` 记录每篇的算法版本，`--redo-version` 只挑版本更低的。

## 6. 与下游的契约

| 事项 | 约定 |
|---|---|
| 条目 frontmatter | `kp_count`（含 0）+ `kp_version`；`scan` 据此判断「已判定过」，0 条不再判 P1 |
| 知识点 frontmatter | `kp_type` / `kp_reuse` / `kp_why` / `kp_score`（融合）/ `kp_rule_score` / `kp_ai_value` / `kp_version` |
| 机器可读结果 | `kp_extract` 每篇打印 `KP_RESULT sha12=… n=… cands=… cov=…`；0 条也算成功 |
| 条数变少 | 删旧文件 + `index_one_entry.py --prune <sha12>` 清索引孤儿 |
| 索引字段 | `index_one_entry.py` 现在同时写 `parent` / `evidence`（此前增量索引漏写，API 里恒为 null） |

## 7. 已知限制

1. **规则分看不见「学术品味」**：判断「这个机制解释是否新颖」仍靠模型 —— 这正是保留 40% 主观权重的原因。
2. **团队画像需要维护**：`config/team_focus.yaml` 决定了「团队相关」分，研究方向变了要同步改；
   改完立即生效（无缓存）。
3. **证据行号两套口径**：API 管线是「清洗后带行号文本」的行号，Agent 管线是「原文行号」，
   两者不通用；`evidence` 目前只作人工回溯用，不做自动对齐。
4. **英文论文的知识点此前是中文**：v2 起改为英文（存量条目未回填，重跑即可）。

## 8. 两种模式的共用内核（2026-10-23 追加）

**目标（用户口径）**：API 模式与 Agent 模式**入库效果相同**。因此要共享的不只是提示词，
还有工具与代码。

### 8.1 三层共用

| 层 | 位置 | 谁在用 |
|---|---|---|
| 提示词真源 | `config/prompts/kp_candidates.md` | `kp_extract`（12:01/18:01 的 `GeoKB-InboxIngest` → `inbox_ingest.py`）读取；skill `geokb-kp-writing` 自动镜像 |
| 筛选判据 | `scripts/kp_select.py` | 两条链路都过 `score_candidate` / `check_kp` / 60-40 融合 |
| **落盘内核** | `scripts/kp_store.py` | `kp_extract` 与 `agent_ingest.py kps` **同一个函数**：`write()` / `render()` / `index()` |

统一前两边是两套实现，产出结构不同：

| 字段 | 旧 API | 旧 Agent |
|---|---|---|
| `summary` | `body[:200]` | 全文 |
| `tags` | 自有标签 + 论文标签，截 6 | 仅自有标签 |
| `sources` | 条目自带（PDF 链接正确） | 自建，url 指向 `kp-xxx/pdf`（**必然 404**） |
| `kp_score`/`kp_rule_score`/`kp_ai_value` | 有 | 全缺 |
| `evidence` 缺省 | 不写 | 写「（未定位）」 |
| 模板 | 含「条目 `paper-xxx`」、原文依据、期刊年份 | 精简版 |

统一后两种模式只差 `extraction` 一行（`deepseek-kp` / `agent-kp`），其余逐行一致。

### 8.2 校验工具

```bash
python scripts/kp_prompt.py --check        # 真源 ↔ skill 镜像一致、kp_extract 确实读文件
python scripts/kp_prompt.py --sync-skill   # 改完真源后同步 skill 受管区块
python scripts/kp_store.py                 # 落盘内核自检（字段/模板/sources）
python scripts/kp_parity.py --sha <sha12>  # 同篇两种模式渲染对拍，应只差 extraction
python scripts/kp_parity.py --audit 300    # 全库字段覆盖率（暴露历史遗留）
```

### 8.3 元数据补全

旧条目常缺 `journal` / `year`（早期 Agent 写入没带），`kp_store.paper_meta()` 从 PDF 路径
`by_journal/<期刊>/<年>/` 或 `Addition/<年>/` 反推，比读台账可靠（台账无 sha1 字段）。

### 8.4 历史遗留（未回填）

全库 300 条抽查：`kp_type` / `kp_reuse` / `kp_score` / `kp_rule_score` / `kp_ai_value` /
`kp_version` 覆盖率 **0%**（v1 算法没写这些字段），`year` 60.3%。
这些字段可用 `infer_type` / `infer_reuse` / `score_candidate` 从现有正文反推回填，
但 `kp_version` 应标 `1.0`（未按 v2 重跑），否则会被误认为已重算。
